# 第一章 项目概述

> 官方对应：项目概述——背景与意义、目标定位。  
> 主要评分：创新性20分、需求分析15分、应用效果15分。

## 1.1 项目背景与行业现状

### 1.1.1 智慧文旅从信息查询走向现场决策

- 说明景区游客需求由“票价多少、景点介绍”转向“带特定同行人，在限定时间内如何安全完成游览”。
- 分析文旅决策具有位置、时间、体力、坡度、演艺场次和离园死线等强物理约束。
- 点明生成式大模型擅长语言理解，但不能天然保证路线连通、时间守恒和无障碍安全。

### 1.1.2 现有方案的能力边界

从同一组维度比较：

- 静态导览图：信息固定，无法理解个体需求；
- FAQ/关键词问答：能回答事实，不能组合约束；
- 普通 RAG：能提供知识依据，但不负责路线物理可行性；
- 通用大模型路线生成：表达自然，但可能编造距离、时间和通行条件；
- 传统最短路：能算路径，但不理解自然语言、演艺偏好和人群差异。

### 1.1.3 项目的必要性与价值

- 民生价值：降低老人、儿童、轮椅和行动不便游客的游览风险。
- 行业价值：减少路线误导、赶场失败和事实口误造成的体验损失。
- 技术价值：探索大模型与确定性运筹算法协同的可信智能体范式。
- 推广价值：可迁移至博物馆、主题乐园、历史街区、会展和大型园区。

## 1.2 创新场景定义

### 1.2.1 场景名称

面向真实景区的可信文旅决策场景。

### 1.2.2 典型任务

以“带腿脚不便的老人、限定时间、需要观看指定演出、避免大坡和台阶、按时离园”为代表任务，说明系统必须同时完成：

- 听懂自然语言；
- 补齐关键状态；
- 获取可信事实；
- 计算真实可走路线；
- 判断能否按时完成；
- 在不可行时解释原因并给出替代方案。

### 1.2.3 场景新颖性

- 从“知识回答”升级为“任务决策”；
- 从“语言上合理”升级为“物理上可验证”；
- 从“必须给答案”升级为“能诚实拒绝”；
- 从“只展示结果”升级为“全过程可追溯、可复现”。

## 1.3 项目目标定位

### 1.3.1 总体目标

构建一个能够理解游客个体约束、查证景区事实、生成可执行路线并对不可行请求进行安全降级的可信文旅决策智能体。

### 1.3.2 技术目标

- 建立13维游客场景状态表达与关键槽位追问机制；
- 建立向量、结构化、关键词三路并行混合检索；
- 建立基于数字孪生路网的多约束规划器；
- 建立LLM越权拦截和14项形式化验证；
- 建立问答、状态、规划和全链路Trace评测体系。

### 1.3.3 产品目标

- 提供事实问答与证据追溯界面；
- 提供路线时间轴、约束说明和交互追问界面；
- 支持Live2D数字人、语音交互与外部实景导航调起；
- 形成可部署、可演示、可评测和可扩展的端到端原型。

### 1.3.4 预期效益

分别说明社会效益、游客体验价值、景区运营价值和跨场景推广潜力。涉及成本、收益和回收期时必须标注为情景测算，不写成已实现经营结果。

# 第二章 需求分析

> 官方对应：需求分析——问题剖析、用户需求调研。  
> 主要评分：需求分析15分、创新性20分。

## 2.1 问题剖析

### 2.1.1 物理常识盲区

- 直线距离不等于真实通行距离；
- 路线可能包含台阶、陡坡或不连通路段；
- 对老人和轮椅游客而言，错误路线可能造成安全和体力风险。

### 2.1.2 时效与演艺错配

- 只看演出开始时间，不考虑步行、排队、安检和停检缓冲；
- 只做前向推荐，无法回答“最晚几点必须出发”；
- 临时延误后缺少动态纠偏和替代方案。

### 2.1.3 垂直事实口误

- 票价、演出时刻、开放时间和专有名词容易被大模型误写；
- 单一向量检索对精确数字和字段事实存在盲区；
- 多信源冲突时缺少权威裁决和证据追溯。

### 2.1.4 决策责任缺失

- 普通系统倾向于生成“看起来完整”的答案；
- 缺少对时间、距离和可达性的形式化校验；
- 缺少明确的不可行状态、拒绝原因和替代路线。

## 2.2 用户与利益相关方分析

### 2.2.1 目标游客

- 普通自由行游客；
- 携带老人或儿童的家庭；
- 轮椅、婴儿车及其他行动受限群体；
- 有明确演艺、打卡或离园时间要求的游客。

### 2.2.2 景区运营方

- 需要统一维护景点、道路、演艺和设施信息；
- 需要减少误导、客诉和重复人工咨询；
- 需要低成本、可维护、可逐步接入现有系统的方案。

### 2.2.3 导游与服务人员

- 需要可信的信息辅助和复杂任务决策支持；
- 系统应辅助人工，不宣称完全替代导游或现场管理人员。

## 2.3 用户需求调研

### 2.3.1 调研方法

- 说明问卷、访谈、案例分析或现场观察方法；
- 交代时间、对象、样本量、渠道、题项和分析方法；
- 说明匿名化、自愿参与和隐私保护方式。

### 2.3.2 探索性预调研结果

引用 `n=50` 预调研时必须同时写明：

- 这是探索性预调研，不代表全体游客；
- 每个百分比同时给出分子、分母；
- 不把需求意愿解释为系统满意度或实际使用效果；
- 定性访谈只使用有编号、可追溯且已获授权的材料。

### 2.3.3 需求优先级

按以下顺序组织：

1. 安全与硬约束：无障碍、时间预算、离园死线、演艺时间窗；
2. 可信性：官方事实、证据来源、规则校验、不可行解释；
3. 可用性：自然语言交互、主动追问、清晰时间轴；
4. 体验性：个性偏好、Live2D、语音和文化表达；
5. 运营性：低成本部署、数据更新、Trace审计和跨景区迁移。

## 2.4 需求规格

### 2.4.1 功能需求

- 事实问答与证据追溯；
- 13维场景状态抽取；
- 缺失信息澄清；
- 多约束路线规划；
- 无障碍路径过滤；
- 演艺时间窗与排队缓冲；
- 诚实拒绝与优雅降级；
- 动态重规划；
- 路线时间轴与导航调起。

### 2.4.2 性能与质量需求

- 检索、规划和页面响应的可测量指标；
- 相同结构化输入的确定性与可重复性；
- 关键硬约束违规必须为0；
- 失败和降级必须进入Trace，不能静默隐藏。

### 2.4.3 合规与伦理需求

- 最小化收集游客个人信息；
- 不保存未经授权的敏感身份和人脸数据；
- 明示系统不替代现场安全管理和官方公告；
- 对行动受限群体采用更保守的路线边界；
- 对未现场核验的道路和设施标注估算或待核验状态。

# 第三章 解决方案设计

> 官方对应：解决方案设计——技术路线规划、系统架构设计、功能模块设计。  
> 主要评分：解决方案可行性20分、创新性20分。

## 3.1 技术路线规划

### 3.1.1 总体技术路线

```text
游客自然语言输入
→ 13维状态抽取与置信度门禁
→ 三路混合检索与权威事实校验
→ 倒排时空约束推演
→ Dijkstra可达路径计算
→ 24宽Beam Search景点组合优化
→ 14项形式化验证
→ 可行路线 / 追问 / 诚实拒绝与替代方案
→ 双屏前端呈现与Trace审计
```

### 3.1.2 技术选型原则

- LLM用于非结构化语义理解和用户化表达；
- 确定性算法用于距离、时间、路网和可行性裁决；
- 检索系统用于外部事实与证据约束；
- 形式化规则用于最终安全门禁；
- 前端用于解释、交互和导航衔接。

每项技术选择都要说明“为什么适合该问题”和“为什么不能由其他模块替代”。

### 3.1.3 双引擎软硬解耦

- 语义软引擎：自然语言理解、13维状态画像、文化互动和结果解释；
- 决策硬引擎：路网搜索、时间计算、多目标优化和形式化验证；
- 权限边界：LLM不得直接决定 `steps`、`feasible` 等关键路线结果；
- 协同机制：LLM只提交经过Schema校验的状态，规划器输出结构化路线，LLM只负责忠实解释。

## 3.2 系统架构设计

### 3.2.1 五层架构

1. 表现层：`QAPage`、`RecommendPage`、Live2D、语音与地图导航；
2. 状态层：Scene Extractor、13维状态、置信度门禁和交互追问；
3. 知识层：三路并行检索、RRF、Cross-Encoder和官方指南裁决；
4. 规划层：路网过滤、倒排推演、Dijkstra、Beam Search和动态重规划；
5. 底座层：数据契约、Route Validator、Trace、评测资产与部署环境。

### 3.2.2 数据流与控制流

- 区分事实问答链路和路线决策链路；
- 标明输入、输出、Schema、API和模块边界；
- 标明哪些步骤可由模型参与，哪些步骤必须由确定性代码裁决；
- 标明失败、超时、低置信度和不可行请求的分支。

### 3.2.3 部署架构

- 游客端Web/移动端；
- Node.js/TypeScript业务与规划服务；
- Python向量检索服务；
- 景区侧轻量边缘规划节点；
- 云端大模型API；
- 本地知识、路网、评测和Trace资产。

若引用“4核节点”和吞吐指标，必须注明测试对象是纯路线规划接口，不包含LLM、ASR、TTS等全链路。

### 3.2.4 可扩展性与稳定性

- 知识、景点、道路和演艺均采用结构化契约；
- 新景区以数据替换和规则配置为主，避免重写核心算法；
- 检索通道和规划器职责解耦；
- 服务异常有明确降级，Trace记录真实执行状态。

## 3.3 功能模块设计

### 3.3.1 13维场景状态理解

- 定义13维状态字段及其业务意义；
- 说明规则抽取、LLM抽取和Schema校验的协同方式；
- 说明置信度阈值与关键槽位缺失判定；

- 当前评测以受控数据集为主，不能代表全体游客真实体验；
- 动态客流、天气、施工和临时闭园信息尚未完整接入；
- 云端模型服务受网络与Provider稳定性影响；
- 商业收益属于情景测算，尚需运营方试点验证。

## 7.4 未来规划

### 7.4.1 近期

- 完成目标道路边补齐和现场核验；
- 在最新代码提交上重新冻结全套正式评测；
- 完成受控可用性测试和演示流程预演；
- 对接景区官方演艺、设施和临时公告数据。

### 7.4.2 中期

- 接入实时客流和动态重规划；
- 建立运营方知识与路网维护后台；
- 开展真实游客任务完成率、SUS和信任度评测；
- 推进景区试点、合作证明和知识产权成果。

### 7.4.3 长期

- 迁移到博物馆、历史街区、主题乐园和大型园区；
- 研究动态不确定环境下的鲁棒时空规划；
- 建立面向公共空间决策智能体的可信评测标准。

## 7.5 收束表达

> 大模型负责听懂游客，检索系统负责查准资料，规划算法负责算出能走的路线，验证器负责拦截错误。灵小禅的目标不是成为最会说话的导游，而是成为一个不会乱带路、能够对现实约束负责的智能导游。
