| 官方作品要求 | PPT落实方式 |
| --- | --- |
| 聚焦场景创新 | P2讲真实未满足需求，P3讲从问答到决策的场景升级 |

### 1.3 汇报主线

整套PPT只讲一条因果链：

```text
现实文旅问题
→ 普通大模型为什么会“乱带路”
→ 双引擎如何分工
→ 检索如何查准事实
→ 状态理解如何听懂游客
→ 运筹算法如何算出能走的路线
→ 验证器如何拦截错误
→ 实验如何证明可靠
→ 产品如何落地并复制
```

评委最终应记住：

> 大模型负责听懂游客，检索系统负责查准资料，规划算法负责算出能走的路线，验证器负责拦截错误。

### 1.4 全局表达原则

1. 每页只回答一个核心问题，只保留一个视觉焦点；
2. 标题写结论，不使用“技术架构”“实验结果”等空泛名词；
3. 每项技术必须和一个具体场景痛点绑定；
4. 每个关键数字必须能回到原始证据文件；
5. 实测、探索性调研、商业测算和未来目标必须明确区分；
6. 不把算法名本身当作创新，创新是它们形成的可信决策闭环；
7. 不用大段论文式文字，页面负责呈现证据，讲解负责补充逻辑。

# P1 封面｜把“景区问答”升级为“可信文旅决策”

## 页面任务

在第一眼建立项目定位，避免被评委理解成普通数字人、聊天机器人或景区知识问答系统。

## 建议结论标题

> 灵小禅：一个不会乱带路的可信文旅决策智能体

## 页面内容

- 项目全称：灵小禅——灵山胜境可信文旅决策智能体；
- 核心副标题：从单点事实问答到物理时空多约束规划；
- 一句话机制：大模型理解游客，运筹引擎负责路线，验证器拦截错误；
- 参赛赛道、团队、学校和指导教师信息。

## 主视觉

- 灵小禅数字人立绘与灵山实景结合；
- 叠加一条从“自然语言”流向“可信路线”的细线数据流；
- 画面中心只突出“可信决策”四个字。

## 对应评分

- 创新性20分：先建立“问答→决策”的范式差异；
- 应用效果15分：提前传达项目面向真实游客任务。

## 讲述重点

“我们不是让大模型推荐几个景点，而是要求系统对路线是否赶得上、老人能不能走、演出会不会错过负责。”

## 表述红线

- 不写“全国首创”“行业第一”，除非有权威检索与证明；
- 不把数字人形象当作核心创新。

# P2 痛点｜游客需要的不是景点介绍，而是不会翻车的现场决策

## 页面任务

用真实用户需求证明项目必要性，命中官方“问题剖析深入、需求调研科学”的高分要求。

## 建议结论标题

> 三类文旅“翻车”同时发生，普通导览无法对结果负责

## 页面内容

三张痛点卡：

1. 物理盲区：老人、轮椅或婴儿车被台阶和陡坡阻断；
2. 时效错配：低估步行和排队时间，错过演艺或离园接驳；
3. 事实口误：票价、场次和开放时间出现错误或冲突。

底部增加探索性预调研数据条：

- 错过演艺或时效误判：82.0%（41/50）；
- 遇到台阶或陡坡折返：66.0%（33/50）；
- 遇到通用AI事实失准：74.0%（37/50）；
- 愿意使用可信决策导览：90.0%（45/50）。

## 证据标注

- 明确写“探索性预调研，n=50，不代表全体游客”；
- 页面脚注引用 `pre_survey_summary.md` 和调研协议；
- 访谈原声只使用有编号、可追溯且已授权的材料。

## 主视觉

- 三列“翻车现场”卡片；
- 每列包含游客问题、失败后果和一个核心数据；
- 朱砂红只用于风险点，避免满页警示色。

## 对应评分

- 需求分析15分；
- 创新性20分中的场景独特性。

## 讲述重点

“这些问题不是回答得好不好听，而是游客会不会走冤枉路、错过演出，甚至承担安全风险。”

## 表述红线

- 不把预调研写成全国游客调查；
- 不把使用意愿写成系统满意度或应用效果。

# P3 破局｜让模型理解语义，让算法裁决现实

## 页面任务

提出项目最有辨识度的总解法，完成从痛点到方案的逻辑跃迁。

## 建议结论标题

> 双引擎软硬解耦，让生成式AI第一次对物理可达性负责

## 页面内容

用三角色结构说明职责：

- 大模型：理解自然语言、抽取13维状态、组织文化表达；
- 运筹引擎：计算路网、时间、坡度、演艺和多目标组合；
- 形式化验证器：校验14项守恒规则，决定是否放行。

中央写出代码级权限边界：

```text
LLM可以理解和解释
但不能直接生成 steps / feasible 等关键规划结论
```

## 主视觉

- 左“语义软引擎”、右“物理硬引擎”、下“验证门禁”；
- 用锁形图标表现 `FORBIDDEN_LLM_FIELDS`；
- 用一句大字突出“模型没有路线裁决权”。

## 对应评分

- 创新性20分；
- 解决方案可行性20分。

## 讲述重点

“我们没有试图让大模型更大胆地编路线，而是从系统架构上限制它的权力。”

## 表述红线

- 不说Dijkstra、RRF或Beam Search本身是原创算法；
- 创新点应表述为组件组合后的可信决策机制与责任边界。

# P5 检索机制｜三路并行检索同时覆盖语义、字段和专名

## 页面任务

说明系统如何获取可信事实，并证明技术选择与文旅问题高度适配。

## 建议结论标题

> 三路并行召回、统一融合、权威裁决，把“找得到”升级为“查得准”

## 页面内容

严格展示当前链路：

```text
Query Rewrite
→ Promise.all并行执行
   ├─ Vector：处理语义与口语表达
   ├─ Structured：处理票价、时间、设施字段
   └─ Keyword：处理景点和演艺专名
→ RRF融合（k=60）
→ Cross-Encoder重排
→ 官方指南权威兜底
```

右侧放三个典型问题：

- “哪里适合老人慢慢逛？”对应Vector；
- “几点开演、是否无障碍？”对应Structured；
- “九龙灌浴/吉祥颂”对应Keyword。

## 主视觉

- 左侧三路并行管线；
- 右侧问题类型与通道适配表；
- 底部突出RRF和官方指南裁决。

## 对应评分

- 解决方案可行性20分；
- 创新性20分中的技术适配。

## 讲述重点

“三路不是为了堆模块，而是因为文旅问答同时存在语义问题、字段问题和专名问题。”

## 表述红线

- 不将RRF描述为生成知识；
- 不声称官方指南能覆盖全部动态事实；
- 不把配置存在等同于模块真实执行，执行状态应由Trace证明。

# P6 检索对比｜任何单一路径都有盲区，互补才是关键

## 页面任务

通过问题类型对比解释混合检索的必要性，为P7量化消融建立逻辑基础。

## 建议结论标题

> 向量懂语义、结构化守事实、关键词抓专名，单路都无法覆盖完整文旅问题

## 页面内容

建议使用对比矩阵：

| 问题类型 | Vector | Structured | Keyword | 完整方案 |
| --- | :---: | :---: | :---: | :---: |
| 口语与同义表达 | 强 | 弱 | 中 | 强 |
| 精确票价与时间 | 中 | 强 | 中 | 强 |
| 景点与演艺专名 | 中 | 中 | 强 | 强 |
| 多信源融合 | 弱 | 弱 | 弱 | 强 |
| 权威冲突裁决 | 无 | 局部 | 无 | 官方指南兜底 |

补充一组同题对比：

- 单一向量：可能召回意思相近但数字不准的文本；
- 单一结构化：遇到口语表达时覆盖不足；
- 单一关键词：容易命中专名但缺少语义理解；
- 完整方案：多通道互补后再重排。

## 主视觉

- 中央对比矩阵；
- 右下角只保留一句结论：“互补机制，而非模块数量”。

## 对应评分

- 解决方案可行性20分；
- 创新性20分；
- 为测试与验证10分铺垫。

## 讲述重点

“这一页解释为什么要混合，下一页用受控消融说明各配置真实表现。”

## 表述红线

- 机制对比与实测数据分开；

# P7 消融实证｜七组受控实验公开完整方案，也保留反直觉结果

## 页面任务

证明项目具备严格控制变量、保留失败与诚实解释实验的能力。

## 建议结论标题

> 完整方案取得98.0%受控观察值，实验同时保留同分项与失败边界

## 页面内容

完整展示7组结果：

| Profile | Accuracy | Fact Recall | Avg Latency |
| --- | ---: | ---: | ---: |
| Vector only | 94.0% | 0.960 | 2336.08ms |
| Structured only | 66.0% | 0.694 | 2172.20ms |
| Keyword only | 96.0% | 0.977 | 2221.56ms |
| Full retrieval | 98.0% | 0.980 | 2882.68ms |
| Vector + Rerank | 94.0% | 0.950 | 2873.62ms |
| Full without Rerank | 90.0% | 0.933 | 2358.02ms |
| Full without Rewrite | 98.0% | 0.993 | 2414.48ms |

必须给出三条严谨解读：

1. 98.0%是特定受控运行观察值，不是全域准确率保证；
2. Full without Rewrite同样为98.0%，本轮实验不能证明Rewrite必然提高准确率；
3. Full retrieval相对Full without Rerank高8个百分点，是本轮观察，不外推为普遍因果结论。

## 主视觉

- 以Accuracy柱状图为主；
- Fact Recall用小点或细线辅助；
- Latency放次级标注，不建议用复杂双轴制造视觉误导；
- Full retrieval用琉璃金突出，Full without Rewrite用虚线强调“同分事实”。

## 对应评分

- 测试与验证10分；
- 解决方案可行性20分。

## 讲述重点

“我们不只展示最好看的数字，也保留同分项、失败样本和模型随机性边界。”

## 证据来源

- `evaluation/results/ablation_20260917_013925/`；
- `docs/ablation_report.md`；
- 检索组件消融实验对比报告。

## 表述红线

- 不把98.0%写成权威基线，权威50题基线是96.0%；
- 不删除或弱化Full without Rewrite的98.0%；
- 不使用人为平滑或重排后的虚构数据。

# P9 路线运筹｜先过滤走不了的路，再倒推来不来得及

## 页面任务

证明路线生成依赖真实路网、时间窗和硬约束，而不是大模型文本补全。

## 建议结论标题

> Dijkstra管“能不能走”，倒排推演管“来不来得及”，Beam Search管“怎么组合更优”

## 页面内容

四步算法漏斗：

1. 路网建模：路线节点、道路边、米数、步行时间、坡度和无障碍属性；
2. Dijkstra：过滤台阶、陡坡和不可达边，计算可行路径；
3. 倒排时空：从离园死线、演艺开始和排队缓冲反推最晚到达与出发时间；
4. 24宽Beam Search：在可行候选中平衡必去点、演艺、兴趣、体力、距离和时间。

底部增加14项形式化验证：

- 时间守恒；
- 路网连通；
- 无障碍与坡度；
- 演艺窗口和排队缓冲；
- 必去点与离园死线；
- 总时间、里程和步骤一致性。

## 数据口径

- 当前仓库可核验资产：23个路线节点、30条当前登记道路边；
- 31条为待补齐核验的目标口径；
- 发布前如资产变化，必须以冻结清单和最新Route Benchmark为准。

## 主视觉

- 左侧路网图；
- 中间四层算法漏斗；
- 右侧倒排时间轴；
- 底部验证器盖章“PASS / REJECT”。

## 对应评分

- 创新性20分；
- 解决方案可行性20分。

## 讲述重点

“硬约束先决定哪些路线不能走，软偏好只在可行路线之间做选择。”

## 表述红线

- 不把估算道路数据写成官方高精实时导航；
- 不把31条目标边写成当前已核验资产；
- 不说Beam Search能保证全局最优，应表述为受控搜索空间中的高质量候选优化。

# P11 英雄案例｜赶得上就给路线，赶不上就给证据和替代方案

## 页面任务

将前面的算法串成一个评委能记住的真实任务，形成全场叙事高潮。

## 建议结论标题

> 面对老人、演艺和离园死线，系统不仅给路线，更证明为什么可行

## 主案例输入

> “我带腿脚不方便的妈妈，现在在正门，下午四点前要离园，还想看两点的《吉祥颂》，怎么走？”

## 页面内容

主时间轴必须展示：

- 起点与当前时间；
- 每段真实路网米数和预计步行时间；
- 最大坡度、台阶情况与无障碍判定；
- 景点停留时间；
- 演艺开始、持续时间和15～20分钟排队缓冲；
- 最晚离开和离园时间；
- 14项验证结果。

右下角增加20分钟不可达对照：

```text
判定不可行
→ 说明时间与路程冲突
→ 拒绝超时目标
→ 推荐附近18分钟左右的微游览
```

## 数据填充规则

- 路线、米数、时间和坡度必须从发布前冻结的Route Planner输出与路网数据提取；
- 估算值必须标“Estimated”；
- 不直接沿用旧PPT中的手工数字；
- 若最新输出变化，时间轴、讲稿和演示视频必须同步更新。

## 主视觉

- 70%版面用于主案例时间轴；
- 30%版面用于不可行请求的红色分支；
- 用绿色“验证通过”和红色“拒绝并降级”形成对照。

## 对应评分

- 应用效果15分；
- 创新性20分；
- 需求分析15分。

## 讲述重点

“诚实拒绝不是系统失败，而是可信智能体不越过物理边界的能力。”

## 表述红线

- 不编造现场实测路线；
- 不把算法输出称为官方导航；
- 不为了视觉完整强行安排不可行景点。

## 九、最终表达红线

1. 不把项目讲成“套壳大模型+数字人”；
2. 不把单个常见算法包装成原创算法；
3. 不编造竞品准确率、用户评价或现场经营效果；
4. 不把96.0%基线和98.0%受控观察值混为一谈；
5. 不删去消融中的同分项、失败项和限制；
6. 不把估算路网写成官方实时地图；
7. 不把31条目标道路边写成当前已核验资产；
8. 不把纯规划接口QPS写成大模型全链路性能；
9. 不把探索性预调研写成全体游客统计；
10. 不把商业情景测算写成已实现收益；
11. 不让LLM在表达中越权成为路线可行性的最终裁决者；
12. 不删除“不可行、主动追问、诚实拒绝和人工复核”等可信边界。
