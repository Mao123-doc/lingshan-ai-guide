# 《灵小禅》竞赛汇报 PPT 制作说明

## 1. 文档用途

这份文档交给 PPT 制作者使用，目标是先完成一版可用于答辩排练的初版 PPT。制作重点是把项目讲成一个完整的“AI+景区场景创新”方案，而不是把代码、功能和技术名词堆在一起。

比赛方向：人工·智能算法精英大赛——AI+场景创新赛道。

项目名称：灵小禅——面向真实景区复杂游览场景的 AI 数字人导游。

项目定位建议统一为：

> 面向真实景区复杂游览场景，构建融合多路知识检索、游客状态理解和多约束路线规划的 AI 数字人导游系统，让 AI 从“回答旅游问题”进一步走向“理解游客、规划行程、辅助游览决策”。

整套 PPT 必须围绕这条因果链展开：

```text
真实景区痛点
    ↓
普通导览为什么解决不好
    ↓
AI 场景方案
    ↓
三项核心能力
    ↓
实验验证
    ↓
真实游客案例
    ↓
产品闭环与推广价值
```

## 2. 最重要的表达原则

### 2.1 先讲场景，再讲技术

开场先让评委理解游客在景区中遇到的真实问题，再说明为什么需要 AI。不要一开始展示 RAG、向量数据库、模型名称或后端框架。

建议围绕以下三类问题建立场景：

- “我带着老人，只有三个小时，应该怎么游览？”
- “演出马上开始，我现在应该先去哪？”
- “附近有没有适合行动不便游客的路线和设施？”

这些问题同时涉及景区知识、游客状态、时间限制、空间关系和路线决策，这就是项目的场景价值。

### 2.2 把核心创新收敛为三件事

全篇不要平均强调十几个功能，重点只讲三项能力：

1. **多路知识检索**：根据问题类型组合 Vector、Keyword、Structured Retrieval，并通过 Rerank 和 LLM 生成回答。
2. **游客状态理解**：从自然语言中提取年龄、行动能力、时间、偏好、必去景点、已游景点等信息。
3. **多约束路线规划**：综合当前位置、时间预算、演出时间、必去景点、行动能力和路线限制，生成可执行的游览方案。

数字人、语音、图片识别、地图和后台是产品落地能力，应该服务于以上三项核心创新。

### 2.3 每一页只证明一个结论

页面标题尽量直接写结论，不要使用没有观点的标题。

不建议：

- 技术架构
- 实验结果
- 项目功能
- 应用前景

建议：

- 多路检索覆盖不同类型的景区问题
- Query Rewrite 使问答准确率提升 10 个百分点
- 路线生成由游客约束驱动
- AI 能把自然语言需求转化为可执行游览方案

## 3. 建议的 14 页 PPT 故事线

| 页码 | 页面标题 | 页面结论 | 建议视觉 | 口头讲解重点 |
|---|---|---|---|---|
| 1 | 灵小禅：面向真实景区复杂场景的 AI 数字人导游 | 这是一个面向真实景区的 AI 导游系统 | 数字人、景区视觉、产品主界面、项目一句话定位 | 说明服务对象、使用场景和核心价值。封面不要堆技术栈。 |
| 2 | 传统景区导览难以处理复杂、动态、个性化需求 | 游客的问题往往同时包含知识、时间、身份和路线限制 | 三个游客问题卡片或漫画式场景 | 说明 FAQ、普通地图和通用问答各自解决不了什么。 |
| 3 | 智能导游需要同时解决知识、理解和决策 | AI 导游的核心任务不是单纯聊天，而是知道景区、理解游客、规划游览 | 三角结构：Knowledge / Understanding / Decision | 把后面三项技术创新与三个真实问题对应起来。 |
| 4 | 构建覆盖“问—懂—查—规划—交互”的 AI 导游闭环 | 游客输入可以转化为知识回答和游览决策 | 极简流程图：文本/语音/图片 → 状态理解 → 检索/规划 → LLM → 数字人/地图 | 只保留业务主链路，不要画几十个工程组件。 |
| 5 | 多路混合检索覆盖不同类型的景区问题 | 不同问题应使用不同的信息获取方式 | Vector、Keyword、Structured → Rerank → LLM | 用票价、景点编号、开放时间、语义问答等例子解释检索分工。 |
| 6 | 单一向量检索存在盲区 | 景区问题中既有语义问题，也有精确事实和结构化数据问题 | 三列对比：问题类型、检索方式、典型问题 | 让不熟悉 RAG 的评委理解为什么需要多路检索。 |
| 7 | 消融实验量化检索组件的实际贡献 | 项目的技术设计可以被实验验证 | 柱状图或折线图，旁边放实验条件 | 重点讲 Query Rewrite、Rerank 对准确率、事实召回和延迟的影响。 |
| 8 | AI 能理解“游客是谁、想去哪、还有多少时间” | 系统可以从自然语言形成游客状态 | 左侧自然语言输入，右侧状态标签卡片 | 展示老人、行动不便、离园时间、演出偏好、必去景点等字段。只展示代码实际支持的字段。 |
| 9 | 路线生成由真实约束驱动 | 路线推荐需要满足现实条件，而不是只生成一段漂亮文字 | 景点节点图、约束标签、路线结果 | 说明当前位置、时间预算、演出时间、行动能力和必去景点如何共同影响路线。 |
| 10 | 用专项评测验证 AI 不仅会说，而且做得对 | 项目建立了知识、场景和路线三个层面的评测思路 | 三张指标卡或评测流程图 | 展示仓库中能核验的测试集、准确率、召回率、约束满足率和延迟。缺数据时不要编造。 |
| 11 | 一个真实游客需求如何转化为完整游览方案 | 三项核心能力会在一个用户案例中协同工作 | 用户需求 → 状态解析 → 知识检索 → 路线规划 → 解释输出 | 建议使用“带老人、时间有限、必须去某景点、想看演出”的复杂案例。 |
| 12 | 核心 AI 能力已经封装为可交互的数字人导游 | 项目已经从算法原型形成可演示产品 | Live2D、语音问答、地图/路线、图片识别截图 | 数字人是交互表现层，重点证明系统可用和可展示。 |
| 13 | 核心能力可以迁移到更多文旅空间 | 更换知识库、POI、路线数据和景区规则后可以复制 | 灵山 → 古镇/博物馆/园区/校园的迁移图 | 讲清楚哪些是场景数据，哪些是可复用的 AI 能力。不要虚构合作和商业订单。 |
| 14 | 让 AI 导游从回答问题走向辅助游览决策 | 用一句话重新收束项目价值 | 三项核心能力 + 三个关键数据 + 产品画面 | 回到“知识、理解、决策”三条主线，留下最强记忆点。 |

## 4. 重点页面的制作要求

### P2：痛点页

不要写成泛泛的“传统旅游体验不够智能”。要让评委看到一个具体游客。

建议页面文案：

> 游客提出的不是一个孤立问题，而是一组同时受身份、时间、偏好和空间关系影响的游览决策。

页面底部可放三个短结论：

- FAQ 能回答固定知识，但难以理解连续需求。
- 地图能提供位置，但不会根据游客状态安排路线。
- 通用大模型能生成语言，但必须接入可信景区知识和现实约束。

### P5-P6：Hybrid RAG 页

不要把“使用 RAG”直接写成创新点。要解释三种检索方式分别解决什么问题：

| 问题类型 | 推荐检索方式 | 例子 |
|---|---|---|
| 语义描述、开放式问答 | Vector Retrieval | “适合老人游玩的景点有哪些？” |
| 景点名称、编号、专有名词 | Keyword Retrieval | “A12 停车场在哪里？” |
| 票价、时间、字段事实 | Structured Retrieval | “老人票多少钱？” |

当前实现更适合表述为“向量优先、结构化和关键词回退/补充的多路检索流程”，不要写成已经完成“三路并行融合”，除非后续代码和实验确实实现了融合。

### P7：消融实验页

这是整套 PPT 最有技术说服力的一页。建议使用同一测试集、同一模型和同一提示词条件下的结果。

当前仓库 `docs/ablation_report.md` 中可以核验到的结果包括：

| 配置 | Accuracy | Fact Recall | Avg Latency |
|---|---:|---:|---:|
| Vector Only | 86.0% | 0.905 | 2543.96 ms |
| Structured Only | 62.0% | 0.697 | 2432.66 ms |
| Keyword Only | 84.0% | 0.908 | 2318.14 ms |
| Full Retrieval | 84.0% | 0.902 | 2923.54 ms |
| Full - Rerank | 84.0% | 0.895 | 2365.80 ms |
| Full - Rewrite | 74.0% | 0.802 | 2411.82 ms |

另外，当前报告记录了 7 个配置、每个配置 50 个问题，共 350 次真实 API 调用；所有配置 API Success Rate 均为 100%。

推荐的结论是：

> Query Rewrite 对当前测试集的 Accuracy 提升 10 个百分点，Fact Recall 从 0.802 提升到 0.902；Rerank 对 Accuracy 影响有限，但使 Fact Recall 提升 0.007，同时增加约 558 ms 延迟。

不要写“Full Retrieval 一定优于 Vector Only”，因为当前报告中的 Full Retrieval Accuracy 为 84%，低于 Vector Only 的 86%。这不是坏事，反而可以体现项目做过真实消融，而不是只挑最好看的数字。

如果后续产生新的正式实验结果，必须同时记录测试集、配置、模型、Prompt 和运行时间，统一替换图表，不能把不同实验批次的数据混在一张图里。

### P8：游客状态理解页

页面不要直接放代码。建议使用“输入—解析—应用”的三段式：

```text
自然语言需求
    ↓
游客状态抽取
    ↓
问答与路线规划共同使用
```

示例输入：

> 我带着奶奶来玩，她腿脚不方便，下午 5 点前要走，还想看演出。

右侧展示结构化状态：

- 老年游客
- 行动不便
- 离园时间 17:00
- 演出偏好
- 低强度路线需求

实际展示的字段必须以代码和接口真实支持为准。

### P9：路线规划页

重点说明“约束如何影响结果”，而不是只放一张路线地图。

建议绘制：

```text
当前位置
时间预算
必去景点
演出时间
行动能力
已游景点
    ↓
路线规划器
    ↓
可执行游览路线 + 预计耗时 + 解释
```

如果仓库中存在正式 route benchmark，展示它的测试规模和约束满足结果；如果暂时只有 Demo，不要把 Demo 结果写成统计结论。

### P11：完整游客案例页

这页不要再讲抽象概念，而要完整复盘一次请求：

> 我带着 70 岁父亲来灵山，只有 3 小时，14:30 想看演出，大佛一定要去，尽量少走路。

展示四步：

1. 识别老人、时间、演出、必去景点和低步行需求。
2. 检索演出时间、景点位置、开放信息和设施信息。
3. 根据路线和时间约束生成可行游览顺序。
4. 由数字人解释推荐理由、预计耗时和注意事项。

这页的作用是把前面的技术全部串回游客价值。

## 5. 视觉与排版规范

### 5.1 整体风格

建议使用“文旅场景 + 克制科技感”的视觉方向：

- 16:9 横版。
- 浅色背景或深色封面，正文保持高对比度。
- 使用一个主强调色，建议结合灵山景区的自然色或品牌色。
- 标题、数据和主图形成明显层级。
- 图表和流程图优先，长段文字最少。
- 可使用山、水、寺院、路径等轻量视觉元素，但不要让装饰压过信息。

避免：

- 大面积廉价霓虹蓝。
- 复杂粒子背景和过多渐变。
- 一页塞十几个功能卡片。
- 大段技术介绍和小字号脚注。
- 与项目无关的网络素材。

### 5.2 每页信息密度

每页尽量控制为：

- 1 个核心结论。
- 1 个主视觉。
- 0～3 个辅助信息。
- 1 个口播重点。

评委只看“标题 + 主图 + 大数字”时，也应该能理解这一页讲了什么。

### 5.3 图表规范

- 坐标轴、单位、图例必须完整。
- 百分比和小数不要混用得没有说明。
- 柱状图只保留必要配置，避免几十根柱子挤在一起。
- 图表旁边直接写结论，不让评委自己找结论。
- 每个数字都能追溯到仓库文档、脚本或实验输出。

## 6. 现场演示建议

现场 Demo 只安排一条完整用户路径，建议控制在 60～90 秒：

1. 游客用自然语言提出复杂需求。
2. 系统显示游客状态解析结果。
3. AI 检索景区知识并回答关键事实。
4. 系统生成路线和安排理由。
5. 数字人通过语音或 Live2D 完成输出。

Demo 重点是证明“问—懂—查—规划—交互”闭环已经实现。提前准备静态截图或录屏作为备份，避免现场网络、模型服务或浏览器权限影响展示。

## 7. 数据与事实使用规则

制作 PPT 前必须以仓库当前代码、文档和实验输出为准，禁止凭印象补数字。

特别注意：

- 当前代码中的 `ALL_SPOTS` 登记数量为 22 个，不要直接沿用旧 README 中未经核对的“30+ 景点”。
- 不要把 350 次 API 调用写成 350 名用户或 350 次真实游客使用。
- 不要把“API Success Rate 100%”写成“系统回答准确率 100%”。
- 不要把当前优先回退式检索描述成三路并行融合。
- 不要把单次 Demo 结果写成用户规模、落地效果或商业合作证明。
- 不要虚构合作单位、真实用户数量、上线景区、商业收入和获奖情况。
- 如果比赛要求匿名，删除学校、学院、指导教师、校徽和可识别参赛单位的信息。

## 10. 最后要记住的表达

整套 PPT 不要围绕“我们做了多少功能”展开，而要围绕下面这句话展开：

> 景区游客面对的是复杂、动态、个性化的游览决策。灵小禅通过可信知识获取、游客状态理解和多约束路线规划，把 AI 从一个会回答问题的聊天机器人，推进为能够辅助游客完成游览决策的数字人导游。
