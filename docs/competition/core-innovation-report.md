# “可信游客决策智能体”竞赛核心创新与展示报告

## 一、报告结论

本项目在场景创新赛道中的最佳定位，不是“一个接入大模型的景区问答系统”，而是：

> 面向真实文旅决策的可信游客智能体。系统能够理解游客的自然语言需求，以知识证据回答问题，把时间、位置、同行人、行动能力和演艺偏好转化为可验证约束，生成可执行路线；当需求无法满足时，系统会主动澄清或解释拒绝原因，并保留完整的检索、生成和评测证据链。

真正值得评委关注的不是单一模型或页面效果，而是系统已经形成了以下闭环：

```text
自然语言需求
  → 场景状态理解
  → 知识检索与事实证据
  → 硬约束路线决策
  → 可行性验证
  → 用户化解释
  → Trace 与 Evaluation 复核
```

这条主线与“AI+场景创新”强调的场景新颖性、技术适配性、应用落地性和效果验证高度一致。根据大赛官网公布的评分规则，主要评分项包括创新性、需求分析、解决方案可行性、项目实施、测试与验证、应用效果和总结展望。[大赛场景创新赛道规则](https://www.aicomp.cn/tracks/tracks-2/3802.html)

## 二、项目解决的真实问题

### 2.1 普通景区问答没有完成游客任务

游客在景区中提出的往往不是单一事实问题，而是带有多个现实约束的决策问题：

- 我现在在哪里；
- 还有多少时间；
- 是否带老人、儿童或轮椅游客；
- 想看哪一场演出；
- 哪些景点必须游览；
- 哪些地点已经去过；
- 如果原计划不可行，应该如何调整。

传统 FAQ、关键词搜索和一般 RAG 问答可以介绍景点，却很难保证路线在时间、路网、演艺场次和行动能力方面真正可执行。

### 2.2 纯大模型路线推荐存在可信度问题

如果把路线规划完全交给大模型，模型可能生成语言流畅但无法执行的路线，例如：

- 把已经错过的演出排入路线；
- 忽略演出持续时间和步行时间；
- 在三小时预算内安排超过三小时的行程；
- 为行动不便游客选择未经确认的路线；
- 在缺少当前时间时直接猜测；
- 为了“给出答案”而隐藏无法满足的条件。

因此，本项目要解决的核心不是“让回答更像导游”，而是“让 AI 在真实旅游约束下作出可信决策”。

## 三、五项核心创新

## 创新一：从“景区问答”升级为“游客决策”

系统不仅回答“灵山大佛多高”“吉祥颂几点开始”，还可以处理完整任务：

> 我带腿脚不方便的妈妈，现在在景区入口，只有三小时，还想看两点的《吉祥颂》，应该怎么走？

系统首先提取结构化 Scene State：

```text
当前位置：景区入口
当前时间：由用户提供或继续追问
剩余时间：180 分钟
同行人：老人
行动能力：limited
演艺偏好：《吉祥颂》14:00
```

随后由路线引擎根据路网、步行时间、景点停留时间、开放窗口和演艺时刻进行决策。

这一创新把项目从“知识服务”推进到“任务完成”，体现了场景创新赛道所强调的实际应用价值。

### 评委可见证据

- 自然语言场景抽取；
- Scene State 结构化结果；
- 带到达、等待、开始和结束时间的路线；
- 多段路径与步行时长；
- 必达点、演艺偏好和时间预算的满足情况。

---

## 创新二：LLM 与确定性规划器协同，而不是让模型独自决策

项目采用“双引擎职责分离”：

| 能力 | 负责模块 | 原因 |
| --- | --- | --- |
| 理解口语问题 | 场景抽取与 LLM | 擅长处理自然表达和语义变化 |
| 景点事实回答 | Hybrid RAG + LLM | 需要知识证据和自然语言组织 |
| 时间预算计算 | 确定性规划器 | 必须稳定、可重复验证 |
| 路网连通与步行时间 | 图搜索与 Validator | 不能依赖模型猜测 |
| 演艺场次与持续时间 | 结构化数据与 Planner | 必须遵守明确时间合同 |
| 无障碍约束 | Route Planner / Validator | 属于高风险硬约束 |
| 最终解释 | LLM 或用户化映射 | 负责把结构化结果说清楚 |

系统中的核心原则是：

> 模型可以理解和解释，但不能绕过硬约束宣布一条路线可行。

路线引擎使用确定性的路径搜索和校验逻辑。演艺持续时间来自结构化演艺合同，而不是用景点游览时长代替；多段路径会逐段验证；相同结构化输入可以重复得到一致结果。

### 差异化价值

很多作品展示的是“模型能生成什么”，本项目展示的是“模型在哪些条件下有权生成，哪些条件必须由算法裁决”。这更接近真实行业系统的安全边界。

---

## 创新三：把“无法满足”设计成一种智能能力

真实游客需求并不总是可行。系统将以下状态明确区分：

```text
feasible                         完全可行
feasible_with_rejected_preferences 部分偏好无法满足，但存在替代路线
needs_clarification              缺少关键决策信息
infeasible                       硬约束下不存在可执行路线
```

例如，游客 10:00 开始游览、只有三小时，却指定观看 14:00 的演出。三小时截止时间是 13:00，系统不会把 14:00 场次包装成可行路线，而会：

1. 明确指出目标演出超出当前时间预算；
2. 保留“未满足演出偏好”的结构化原因；
3. 在其他条件允许时生成一条可执行替代路线；
4. 用普通游客能理解的语言展示，而不是显示内部错误码。

如果用户没有提供当前时间，系统会继续询问：

> 你现在大约几点开始游览？例如“现在上午10点”或“10:00”。

这体现了三层价值：可信拒绝、交互式补全和人本体验。

## 创新四：三路混合检索不是“堆模块”，而是可解释的证据协同

问答系统同时使用三类互补检索：

| 检索通道 | 主要作用 | 典型优势 |
| --- | --- | --- |
| Vector Retrieval | 语义相似召回 | 处理同义表达、口语化提问 |
| Structured Retrieval | 字段级事实召回 | 保证数字、时间、位置等结构化事实 |
| Keyword Retrieval | 精确词匹配 | 保留专名、短词和原文命中能力 |

候选结果通过统一协议融合，再执行 Rerank 和 Context 选择。项目的关键差异在于：每一层不仅“配置存在”，还记录真实执行状态。

Trace 明确区分：

```text
configured=true / false
executed=true / false
status=executed / skipped / failed
reason
result_count
retrieved IDs
rerank 前后顺序
context IDs
generation model
fallback_used
```

因此，评委不仅能看到最终回答，还能追踪“答案为什么产生”。系统不会把 `configured=true` 冒充为模块已经实际执行。

### 竞赛表达

不应说“我们用了向量检索、结构化检索和关键词检索，所以更先进”。更有说服力的表述是：

> 我们为不同类型的事实设计了互补检索通道，并通过统一 Trace 证明每个通道是否真正执行、召回了什么、如何影响最终上下文和回答。

---

## 创新五：把 Evaluation 做成可复现的工程证据链

许多应用型作品只展示几个成功案例。本项目为问答、检索、场景理解和路线规划建立了分层评测：

```text
事实问答：Fact Contract
检索质量：Retrieval Gold Benchmark
场景理解：Scene Gold Cases
路线决策：Route Planner / Validator Benchmark
真实链路：Full-RAG Runtime Smoke
模块贡献：Ablation Profiles
交付质量：API、Build、Browser Journey、git diff gate
```

正式结果保存：

- 数据集与知识库哈希；
- Git commit SHA；
- 实验配置；
- 每题独立 session；
- 原始答案和事实命中；
- Trace 执行状态；
- fallback 使用情况；
- 失败样本；
- 汇总指标。

这种设计使项目可以回答评委最关键的追问：

> 你怎么证明效果来自真实系统，而不是挑选了几个成功演示？

回答是：每个结论都可以回到冻结配置、原始结果、代码版本和失败样本。

## 四、与常见参赛项目的核心差异

| 对比维度 | 常见景区 AI 项目 | 本项目 |
| --- | --- | --- |
| 项目定位 | 景点聊天机器人 | 可信游客决策智能体 |
| 知识获取 | 单一向量检索或 Prompt | Vector + Structured + Keyword 协同 |
| 路线生成 | 模型生成文本路线 | 图搜索、时间预算和硬约束校验 |
| 演艺处理 | 在回答中推荐演出 | 校验开始时间、持续时间和是否赶得上 |
| 适老化 | 文案中写“适合老人” | 将行动能力纳入路径过滤和可行性判断 |
| 信息缺失 | 猜测或直接报错 | 发起自然语言澄清 |

| 可解释性 | 展示最终答案 | 展示检索、排序、上下文和生成 Trace |
| 效果证明 | 成功案例截图 | Baseline、消融、Gold 集、版本化证据 |
| 失败处理 | 隐藏失败 | 保留真实错题、fallback 和限制 |

数字人、语音、视觉识别和管理后台可以增强完整度与展示效果，但这些属于交互和产品支撑层，不应替代上述五项核心创新。

## 七、推荐演示设计

## 7.1 三分钟演示主线

### 0:00—0:25：问题

直接提出真实痛点：

> 景区导览不是“知道多少景点介绍”，而是“能不能根据我现在的情况，告诉我接下来怎么走”。

### 0:25—1:20：可行路线

输入：

> 我带腿脚不方便的妈妈，现在是13:00，在景区入口，只有三小时，还想看两点的《吉祥颂》，应该怎么走？

展示：

- 场景状态；
- 多段路径；
- 到达和等待时间；
- 14:00 开演、按 20 分钟演出时长计算；
- 总步行和总耗时；
- 可行性结果。

### 1:20—2:00：不可行条件

只把当前时间改为 10:00，保持“三小时”和“14:00 演出”。

展示系统识别 13:00 截止时间，明确拒绝 14:00 场次，并给出替代游览路线。强调系统没有为了输出路线而篡改用户需求。

### 2:00—2:30：信息不足

删除当前时间。展示系统询问“你现在大约几点开始游览？”，而不是输出内部字段或生成假路线。

### 2:30—3:00：证据链

快速展示：

- Vector / Structured / Keyword；
- Rerank 前后顺序；
- Context IDs；
- Generation model 与 fallback；
- 50 题 Baseline 和失败样本。

最后落到一句话：

> 我们不仅让 AI 会回答，更让它在真实约束下知道什么能做、什么不能做，并且让每一个结论都能被复核。

## 八、对外表达模板

### 8.1 项目一句话介绍

> 灵山智慧导览是一套面向真实文旅决策的可信游客智能体，通过混合 RAG 理解景区知识，以确定性规划器处理时间、路线、演艺和行动能力约束，并用 Trace 与版本化 Evaluation 保证回答和决策可解释、可验证、可复现。

### 8.2 三个最强创新点

> 第一，从问答走向可执行决策；第二，让 LLM 与确定性约束算法协同，避免生成无法执行的路线；第三，建立从检索、生成到评测的完整证据链，使系统效果可以复现而不是依赖演示案例。

### 8.3 与普通 RAG 项目的区别

> 普通 RAG 解决“从知识库找到答案”，本项目进一步解决“答案在当前游客条件下能否执行”。事实由 RAG 提供，硬约束由 Planner 和 Validator 裁决，最终结果同时包含用户解释和机器可审计证据。

## 九、评委高频问题与建议回答

### 问：为什么不直接让大模型生成路线？

答：语言理解和路线可行性属于不同问题。模型适合理解口语和组织说明，但时间预算、路网连通、演艺场次和行动能力必须稳定验证。因此我们让模型负责理解与解释，让确定性规划器负责裁决硬约束。

### 问：三路检索是不是简单堆叠？

答：三路分别解决不同问题：Vector 处理语义变化，Structured 保证字段事实，Keyword 保留精确专名。系统用统一候选协议融合，并通过 Trace 和消融观察各通道的真实执行和结果，不以模块数量作为创新依据。

### 问：96% 准确率说明什么？

答：它表示冻结的 50 题 Fact Contract 中有 48 题达到独立事实覆盖要求，不能解释为真实游客满意度，也不能解释为所有回答都绝对正确。我们同时保留两道失败题和原始 Trace。

### 问：路线能否作为真实导航？

答：目前可以证明结构化约束和路线算法正确执行，但部分路网和步行时间仍标记为 estimated。现场部署前需要景区运营方核验，因此当前定位是可验证的导览决策原型，不夸大为实时地图导航。

### 问：你们最大的创新到底是算法还是产品？

答：核心是算法与场景边界的共同设计。单独的 RAG、LLM 或最短路都不是新算法，但我们把语义理解、事实证据、确定性约束、可信拒绝和可复现实验组合成面向真实游客任务的完整决策机制。这是场景创新，而不是单点模型创新。

## 十、当前限制与获奖前必须补强的证据

### P0：参赛材料发布前必须完成

1. 在最新路线代码对应的 Git SHA 上重新生成 Scene 与 Route 正式证据；
2. 对正式演示流程完成一次无 fallback 的录屏级预演；
3. 保证所有报告、PPT、视频使用同一组指标、同一提交和同一模型身份说明；
4. 禁止把 estimated 路网描述成官方实时导航。

### P1：决定项目能否从“完成度高”进入“有获奖竞争力”

1. 邀请真实游客完成至少一轮任务测试；
2. 与景区工作人员核验演艺时刻、步行时间、无障碍条件和关键设施；
3. 收集任务完成率、规划耗时、用户理解度和路线接受率；
4. 形成至少一份运营方访谈、试用反馈或合作意向证明；
5. 在演示中展示一个真实错误如何通过 Trace 定位，而不是只展示成功结果。

### P2：增强传播和产品表现

1. 将路线时间线、约束满足和证据来源设计成一屏式可视化；
2. 增加运营方实时更新演艺、拥堵和设施状态的入口；
3. 扩展至博物馆、园区、会展和城市文旅；
4. 建立现场数据版本和过期提醒机制。

## 十一、最终竞赛定位

本项目最有竞争力的地方不是“功能很多”，而是形成了一个完整且诚实的智能决策闭环：

```text
懂游客
  + 有知识依据
  + 遵守现实约束
  + 能承认不可行
  + 会继续追问
  + 可以解释过程
  + 能用实验复核
```

因此，建议最终作品名称、摘要、PPT 和演示视频统一围绕以下定位展开：

> 可信游客决策智能体——面向复杂文旅场景的知识增强、约束规划与可审计 AI 导览系统。

这比“AI 数字人导游”“智能景区问答”更能体现项目已经解决的真实问题，也更容易命中场景创新赛道对创新性、技术适配性、落地性和验证证据的综合评分要求。
