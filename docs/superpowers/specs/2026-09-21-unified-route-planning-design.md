# 统一可信路线规划修复设计

日期：2026-09-21  
状态：已完成方向确认，待用户审阅书面规格  
适用范围：游客路线推荐前端、游客路线 API、Scene State、确定性路线规划器及其测试

## 1. 背景与问题

当前推荐页并存两条互相独立的路线链路：

1. 选择式推荐调用 `POST /api/v1/visitor/recommend`，从 `INTEREST_ROUTES` 固定数组中选取第一项兴趣对应的模板，再按时长截断。
2. 自然语言场景规划调用 `POST /api/v1/visitor/route/plan`，经过 Scene State 抽取、物理路网、Dijkstra、Beam Search 和路线验证器。

这导致选择式推荐中的 `travelType`、`ageGroup`、`budget` 只改变提示文字，不改变路线；多个兴趣只有第一个生效；4、5、6 小时通常都会完整容纳模板，因此返回相同路线。页面却把该结果展示为“按照实际情况推荐”，造成产品承诺与实现不一致。

真正的规划器也存在输入语义不完整的问题：`budget` 和 `pace` 已出现在 Scene State 契约中，但没有进入规划计算；`partyType` 只有情侣场景存在专门加分；“带长辈”如果没有明确说明行动不便，不会触发无障碍约束。这些行为本身未必都错误，但界面没有说明哪些字段是硬约束、软偏好或仅用于提示。

## 2. 目标

本次修复建立唯一可信的路线决策链：

`用户输入（表单或自然语言） → 统一请求规范化 → Scene State → 确定性规划器 → 14 项形式化验证 → 可解释结果`

完成后应满足：

- 生产路径不再直接返回静态路线模板。
- 表单与自然语言表达同一组条件时，进入同一个规划器并得到等价结果。
- 每个可选择字段都有明确语义：硬约束、软偏好或建议信息。
- 不强制不同输入一定产生不同路线；若最优解相同，系统明确说明相关条件如何参与计算。
- 总时长包含步行、游览、等待和演出，不再只累计景点停留时间。
- 时间不足、道路不可达或无障碍条件不满足时，继续诚实拒绝或提供可执行降级方案。
- 保持 23 景点、31 道路数字孪生路网及 14 项形式化守恒为唯一物理依据。

## 3. 非目标

- 不引入未经核验的实时客流、票价、消费价格或地图道路数据。
- 不为了展示“个性化”而人为打乱路线或强制生成不同结果。
- 不将年龄或“带长辈”自动推断为行动不便。
- 不把预算包装成路线约束；在缺少可复现费用数据契约前，预算仅生成消费建议。
- 不改动 RAG 检索架构、事实问答评测基线或 PPT 叙事口径。

## 4. 方案选择

### 4.1 采用方案：统一规划器并保留薄兼容层

选择式表单和自然语言入口都提交到统一的路线规划应用服务。该服务负责请求校验、字段归一化、自然语言抽取结果与显式字段合并、调用 `planRoute`、验证结果和构造解释。

旧 `/recommend` 接口暂时保留，但不得维护独立路线逻辑。它只负责把旧字段转换成统一请求并调用同一应用服务。旧请求缺少当前位置或开始时间时，返回 `needs_clarification`，不得暗设“南门 09:00”等默认事实。

### 4.2 未采用方案

- **继续扩充静态模板**：条件组合会指数增长，无法验证物理可达性，也会继续形成两套事实源。
- **另写一个表单专用评分器**：仍然产生双实现，后续测试、口径和修复容易再次分叉。
- **强制不同画像返回不同路线**：会牺牲最优性和物理真实性，只解决表面观感。

## 5. 统一请求与字段语义

### 5.1 API 请求

`POST /api/v1/visitor/route/plan` 调整为至少接收 `query` 或 `scene_state` 之一，不再要求必须存在非空 `query`：

```ts
interface RoutePlanningRequest {
  query?: string;
  scene_state?: Partial<SceneState>;
  advisory_profile?: {
    ageGroup?: '青年' | '中年' | '老年';
    budget?: '经济型' | '舒适型' | '豪华型';
  };
}
```

纯结构化表单请求不执行 Scene Extraction；返回元数据中的来源扩展为 `explicit`。当自然语言与显式字段共同使用时，来源为 `merged`。该标记只用于审计和界面友好提示，不影响规划分数。

合并优先级固定为：

1. 显式结构化字段；
2. 规则或 LLM 抽取出的字段；
3. 缺失字段保持缺失并触发追问。

显式字段也必须通过 Zod 契约，不允许覆盖 `steps`、`feasible`、`outcome` 等规划器专属字段。

### 5.2 字段分类

| 字段 | 类型 | 规划语义 |
| --- | --- | --- |
| `currentLocation` | 硬约束 | 路线真实起点；缺失时追问 |
| `currentTime` | 硬约束 | 开始时刻及演出时间窗基准；缺失时追问 |
| `remainingMinutes` | 硬约束 | 完整路线时间预算；缺失时追问 |
| `mobility` | 硬约束 | `limited/wheelchair` 过滤不可通行道路和景点 |
| `mustVisitSpotIds` | 硬请求 | 无法满足时明确拒绝该请求，不静默删除 |
| `preferredPerformanceIds/Times` | 带时间窗偏好 | 无法满足时给出原因及不含演出的可执行备选 |
| `visitedSpotIds` | 排除约束 | 不重复安排已参观景点 |
| `interests` | 软偏好 | 所有兴趣共同参与评分，输入顺序不得影响结果 |
| `partyType` | 软偏好 | 仅使用有明确数据或规则支撑的偏好，不推断行动能力 |
| `pace` | 时间策略 | 调整建议停留节奏；不得让步行时间低于路网基准 |
| `mealRequested` | 可满足性请求 | 有设施证据才加入或提示；无数据时明确说明不可验证 |
| `ageGroup` | 建议信息 | 不直接改变物理路线，不推断 mobility |
| `budget` | 建议信息 | 当前只影响消费提示，不宣称改变路线 |

### 5.3 表单字段

路线表单应直接收集：

- 当前位置；
- 开始时间；
- 可游览时长；
- 行动能力：正常、少走路/行动不便、轮椅；
- 游览节奏：轻松、标准、紧凑；
- 一个或多个兴趣；
- 可选的必去景点、演出和已经游览景点；
- 同行类型。

年龄和预算可以保留在“个性化提示”区域，但界面必须标注它们不改变物理路线。不得继续把这两个字段与路线约束并列展示。

## 6. 规划计算规则

### 6.1 唯一应用服务

新增一个路线规划应用服务，集中执行以下步骤：

1. 校验请求至少包含 `query` 或 `scene_state`。
2. 有自然语言时执行 Scene State 抽取；纯表单请求跳过 LLM。
3. 归一化中英文枚举、景点 ID、兴趣和同行类型。
4. 用显式结构化字段覆盖抽取字段。
5. 重算 `missingCriticalFields`，不能沿用覆盖前的缺失列表。
6. 缺少硬约束时返回 `needs_clarification`。
7. 调用 `planRoute` 生成候选路线。
8. 调用 `validateRoute`，硬违规结果不得作为可执行路线返回。
9. 生成证据、条件应用说明和消费建议。

API 层只处理 HTTP 输入输出，不再承载路线模板、字段合并和业务分支。

### 6.2 兴趣与同行偏好

- 兴趣先去重并按稳定键排序，评分按集合计算，保证 `['culture', 'nature']` 与 `['nature', 'culture']` 等价。
- 一个景点可以同时命中多个兴趣，但需设置总偏好加分上限，避免兴趣数量本身压倒步行成本和时间约束。
- 同行类型只能加入软分：亲子偏向已有互动属性的景点，情侣偏向已有浪漫/景观标签的景点。
- “带长辈”不自动套用无障碍过滤；如果行动能力未填写，前端提示用户确认。
- 景点偏好应逐步从名称正则迁移为路网景点上的结构化标签；本次可保留现有正则作为兼容实现，但其输入输出必须封装并接受独立测试。

### 6.3 节奏策略

物理道路的基准步行分钟数不可因“紧凑”而缩短。节奏仅调整可控的建议停留时间：

- `slow`：景点建议停留时间乘以 `1.20` 并向上取整；
- `normal`：使用路网基准停留时间；
- `fast`：景点建议停留时间乘以 `0.85` 并向上取整，但不得低于 10 分钟；演出时长不允许缩短。

同一套时长策略必须同时供规划器和验证器使用，禁止两边各自计算。`limited/wheelchair` 仍通过道路可访问性和景点可访问性执行硬过滤，不由 pace 替代。

### 6.4 候选排序

候选路线继续采用 24 宽 Beam Search。排序优先级为：

1. 无物理硬违规；
2. 满足必去景点；
3. 满足明确演出时间窗；
4. 在时间预算内覆盖更多有效游览价值；
5. 兴趣与同行偏好得分；
6. 更少步行、等待和折返；
7. 稳定 ID 顺序作为最终确定性裁决。

任何软偏好都不能覆盖可达性、开放时间、演出时间窗或总时间预算。

## 7. 返回结果与“为什么相同”

沿用现有 `outcome`、`route`、`explanation`、`evidence` 和 `scene_extraction` 主体结构，并在 `explanation` 中增加：

```ts
interface InputEffect {
  field: string;
  kind: 'hard_constraint' | 'soft_preference' | 'advisory';
  applied: boolean;
  summary: string;
}

interface RouteExplanation {
  input_effects: InputEffect[];
  route_rationale: string[];
}
```

示例说明：

- “已按轮椅条件过滤台阶道路。”
- “文化与建筑兴趣均参与评分。”
- “预算用于消费建议，不改变物理路线。”
- “虽然同行类型发生变化，但当前时间和可达性约束下最优路线仍相同。”

`route_rationale` 只解释当前路线的主导约束，不保存、读取或比较上一位用户或上一请求。是否“与上次相同”由用户观察产生，后端不伪造跨请求判断。前端不得展示内部 Beam Search 分数、trace 字段或实现术语。

## 8. 兼容与迁移

迁移按以下顺序完成：

1. 先建立统一应用服务及差异化回归测试。
2. 调整 `/route/plan` 支持纯结构化请求。
3. 将推荐页表单切换到 `/route/plan`，保留自然语言入口但共用结果组件。
4. 将 `/recommend` 改为薄适配器，返回统一结果结构，并添加弃用响应头。
5. 删除生产路径中的 `INTEREST_ROUTES`；如测试需要固定图数据，应使用测试 fixture，不得留作运行时兜底。
6. 确认没有调用方后，再单独移除 `/recommend`。

迁移期间禁止使用默认当前位置、默认当前时间或模板路线作为无声兜底。缺失关键字段统一进入现有交互追问流程。

## 9. 错误与降级行为

- 请求既无 `query` 又无 `scene_state`：HTTP 400，返回输入错误。
- `scene_state` 契约错误：HTTP 400，并返回可定位的字段错误。
- 缺少位置、时间或时长：HTTP 200，`outcome=needs_clarification`。
- 必去点不可达或超时：`outcome=infeasible`，包含原因和可用备选，不伪造路线。
- 演出偏好无法满足但普通游览可行：`outcome=feasible_with_rejected_preferences`。
- LLM 不可用：自然语言入口使用规则抽取并如实标记 fallback；纯表单入口不依赖 LLM。
- 规划结果出现硬违规：不得返回 `feasible`，记录审计信息并返回不可执行结果。

## 10. 测试策略

### 10.1 请求与接口测试

- 纯 `query`、纯 `scene_state` 和二者合并均能进入统一服务。
- 纯表单请求标记为 `explicit` 且不调用 LLM，混合请求标记为 `merged`。
- 显式字段覆盖抽取字段后重新计算缺失项。
- 空请求和非法枚举被拒绝。
- `/recommend` 与 `/route/plan` 对等价场景返回等价结果。
- `/recommend` 不再返回静态模板响应结构。

### 10.2 差异与不变性测试

- 多兴趣顺序互换，路线和得分结果完全一致。
- 在可控 fixture 中，文化与自然兴趣产生不同最优路线。
- 在可控 fixture 中，180 分钟和 360 分钟产生符合各自预算的路线，较长预算可容纳更多有效行程。
- `limited/wheelchair` 不包含不可访问道路或景点。
- “带长辈 + normal”不被擅自升级为无障碍路线；“带长辈 + limited”触发无障碍约束。
- `slow` 不低估时间；`fast` 不缩短道路和演出时间。
- 预算变化不改变路线，但 `input_effects` 和消费建议明确其 advisory 属性。
- 两组软偏好最终路线相同时，结果仍说明已应用条件且没有虚构差异。

### 10.3 回归门禁

- `npm test --prefix backend`
- 前端推荐页组件测试与前端构建。
- 40 组场景槽位测试保持 100%（40/40）。
- 60 组边界路线测试保持 100%（60/60），物理硬违规保持 0。
- 路线规划对相同输入保持确定性。
- 本次改动不触碰 50 题 Fact Contract 和 7 组 RAG 消融数据；如公共 API 改动间接影响测试启动，必须证明事实问答基线未改变。

## 11. 验收标准

满足以下条件才算修复完成：

1. 推荐页不存在直接消费静态路线模板的生产链路。
2. 表单和自然语言入口共享同一规划应用服务、路网、验证器和结果组件。
3. 所有可见表单字段均有可审计语义；预算和年龄不再被暗示为物理路线约束。
4. 多兴趣全部参与计算且顺序无关。
5. 路线总时长包含步行、游览、等待和演出。
6. 缺失关键事实时追问，不使用猜测默认值。
7. 不可行路线保持诚实拒绝，并提供经过验证的可执行降级方案。
8. 现有场景与路线权威基准全部通过，硬违规为 0。
9. 差异测试能够证明关键条件确实进入计算；相同结果能够被解释，而不是靠强制随机化制造差异。
10. 技术文档和竞赛材料只描述统一后的真实运行链路。

## 12. 预期代码边界

- `backend/src/api/v1/visitor.ts`：删除模板决策职责，只保留 HTTP 适配。

- `backend/src/services/scene/scene-state.ts`：保持 Scene State 权威契约并补充必要归一化映射。
- `frontend/src/pages/visitor/RecommendPage.tsx`：合并两套推荐交互并提交结构化 Scene State。
- `frontend/src/services/api.ts`：定义统一请求和响应类型，标记旧接口弃用。
- 后端、前端测试：增加接口等价、差异、不变性、解释和物理合规测试。

该边界只服务于统一路线决策，不包含无关文件重构。
